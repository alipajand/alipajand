LedgerGuard

Full-Stack AI Contract Intelligence

Senior Product Engineer · built alone · ledgerguard.io

LedgerGuard tracks contract renewals, commitments, notice windows, and financial exposure. I designed and built it alone: the product, the API, the data model, the document pipeline, billing, infrastructure, and delivery.

Five layers under one shipped product. Scroll down through them, or jump to a layer.

LG-01 Layer 1 of 5

Next.js App Router product

Server-rendered product surfaces, with client components only where review interactions need them.

Decision

Draw a hard line in the App Router between server-rendered product surfaces and the client components that handle review interactions.

Trade-off It takes more up-front structure than pushing the whole dashboard into one client-heavy tree, and every new feature has to be placed on one side of the line deliberately.

Sheet LG-01 is a screenshot of the shipped product.

LG-02 Layer 2 of 5

Node.js/Fastify API

Owns deterministic contract data, API rules, authentication, and tenant scoping.

Decision

Keep deterministic contract data and API rules in Node.js/Fastify while isolating probabilistic extraction in the Python worker behind explicit job contracts.

Trade-off The separation adds Redis/BullMQ orchestration, worker lifecycle handling, and more API contracts to maintain.

LG-03 Layer 3 of 5

Supabase PostgreSQL, Auth, Storage

The tenant-scoped data model, where suggested and confirmed values are stored differently.

Every tenant boundary, job contract, and API surface in that list is one I had to define, because there was nobody else to define them.

LG-04 Layer 4 of 5

Redis/BullMQ orchestration and Python extraction worker

Explicit job contracts that let document processing retry or fail independently. AWS Textract and OpenAI extraction, isolated from deterministic contract state.

Decision

Model extraction as an async workflow with visible intermediate states instead of hiding processing behind a single loading spinner.

Trade-off More UI states mean more implementation and copy work across the review flow.

A–A Review boundary

The review boundary

Set the rule the rest of the product follows: suggested values and confirmed values are stored differently, rendered differently, and only cross the boundary through explicit review.

  • Suggested and confirmed values are stored and rendered differently
  • Values cross the boundary only through explicit review
  • The boundary holds across the schema, the API, and the UI

In the product, the line runs through the Document Intelligence Workspace. Terms on the left, the contract on the right: a person confirms, corrects, or flags each extracted term, and only then does it count.

Shipped behaviour it is drawn on: the suggested, verified and corrected statuses and their confirm, edit and needs-review actions; the notice deadline as term end minus notice days, verified only once both of those terms are confirmed or corrected. Proposed, not built: a separate Corrected chip, history and details as tabs, viewer zoom, and moving to the next term after a confirm.

Featured · 01 · 2026–Present

LedgerGuard

Full-Stack AI Contract Intelligence

A multi-tenant contract-intelligence SaaS built alone across the Next.js App Router product, Fastify API, PostgreSQL schema, authentication, billing, and a queue-backed document pipeline. The design problem was keeping probabilistic extraction from becoming confirmed contract data without a human reviewing the evidence.

  1. Note 1

    Keep deterministic contract data and API rules in Node.js/Fastify while isolating probabilistic extraction in the Python worker behind explicit job contracts.

    Result Background extraction can fail or retry independently while deterministic contract state remains controlled by the application and user review.

  2. Note 2

    Draw a hard line in the App Router between server-rendered product surfaces and the client components that handle review interactions.

    Result Route, data, and interaction concerns stayed separable as the workflow grew past the original two screens.

  3. Note 3

    Model extraction as an async workflow with visible intermediate states instead of hiding processing behind a single loading spinner.

    Result Users can tell whether the product is waiting, recovering, or ready for confirmation instead of guessing from a generic pending state.
