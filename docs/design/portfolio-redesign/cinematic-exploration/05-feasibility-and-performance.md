Installed versions, read from `node_modules`: Next.js 16.4.2, React 19.3.1, GSAP 3.15.0, Lenis 1.3.26. **Nothing here is implemented in production.** No production dependency, configuration, Lenis behaviour or page was changed. ## Production transition requirements

From the installed Next.js 16.4.2 guide, `node_modules/next/dist/docs/01-app/02-guides/view-transitions.md`, read for this revision:

- "View transitions work in the App Router with no configuration. React 19.3 includes the `<ViewTransition>` component and `addTransitionType` API." So **no `experimental.viewTransition` flag and no `next.config` change** is needed. `next.config` was not changed, and has no such flag today.
- The guide's browser note: transition types and `view-transition-class` need Chromium 125+ or recent Safari and Firefox; "Without browser support, your application works normally; the transitions do not animate."

What a production version of the story → case morph would need:

1. Wrap the story figure's screenshot and the case hero's screenshot in `<ViewTransition name="lg-shot" share="morph" default="none">`. The guide warns that `default="none"` without `share` "silently stops morphing", so both props are required.
2. Tag the navigations with `<Link transitionTypes={['nav-forward']}>` from the story and `['nav-back']` from the case study's back link, if the two directions should differ.
3. Add `::view-transition { pointer-events: none; }`, so clicks during the 520 ms morph reach the page.
4. Under reduced motion, zero the durations of `::view-transition-old(*)`, `::view-transition-new(*)` and `::view-transition-group(*)`. The site's own motion provider must apply the same rule when the visitor's toggle says off, which the CSS media query alone does not cover.
5. Keep the scroll-linked match cut separate. It runs inside the page and does not need view transitions. The morph happens only on navigation.

**Not verified:** none of this has been built or run in the Next.js app. The integration of `<ViewTransition>` with this site's routing, `RouteChangeFocus` and Lenis is untested.

## Measured cost (lab)

From `capture/perf.mjs`, run on the final revision 2 code: headless Chromium on an Apple-silicon laptop, local static server (uncompressed HTML, CSS and JS), fonts and GSAP from their CDNs. CPU slowdown is Chromium's `Emulation.setCPUThrottlingRate`. Each probe loads the page, then scrolls from the top to the story in 8 s, one `requestAnimationFrame` step at a time, and records every frame interval. Main-thread time is the change in Chromium's `Performance.getMetrics` over that scroll, so it includes the scroll driver itself; the static rows are the baseline for it. These are relative indicators, not field data, and headless frame timing is not a real device's compositor.

| Probe                                | Delivered (KB) | LCP    | CLS   | Frames in 8 s | Median / p95 frame | Frames > 33 ms | Script / style / layout during the scroll (ms) | `will-change` at rest / mid-sequence |
| ------------------------------------ | -------------- | ------ | ----- | ------------- | ------------------ | -------------- | ---------------------------------------------- | ------------------------------------ |
| Desktop 1440×900, live               | 416            | 236 ms | 0.018 | 481           | 16.7 / 16.7 ms     | 0              | 85 / 102 / 6                                   | 0 / 0                                |
| Desktop, 4× CPU slowdown, live       | 416            | 408 ms | 0.018 | 481           | 16.7 / 16.8 ms     | 0              | 304 / 417 / 24                                 | 0 / 0                                |
| 390×844, 4× CPU slowdown, live       | 538            | 364 ms | 0.006 | 481           | 16.7 / 16.8 ms     | 0              | 238 / 172 / 6                                  | 0 / 0                                |
| Desktop, 4×, static (reduced motion) | 352            | 476 ms | 0.018 | 481           | 16.7 / 16.7 ms     | 0              | 273 / 3 / 1                                    | 0 / 0                                |
| 390×844, 4×, static (reduced motion) | 339            | 444 ms | 0.002 | 481           | 16.7 / 16.7 ms     | 0              | 285 / 4 / 1                                    | 0 / 0                                |

Delivered bytes, desktop live: images 169, fonts 87, scripts 66, HTML 47, CSS 47. Scripts are GSAP and ScrollTrigger (already in the production bundle) plus `sequence.js`.

**What this says.**

- **No dropped frames** in any probe, including 4× slowdown at 390 px: every frame interval is at the 60 Hz budget.
- **The sequence's main-thread cost is style recalculation, not script.** Under 4× slowdown, scripting is about the same live as static (the scroll driver dominates both; across three runs of the same probe, scripting varied by up to 200 ms), while style recalculation goes from 3 ms to 417 ms on desktop and 172 ms at 390 px, over an 8-second scroll. The scrubbed timeline writes inline transforms and opacities every frame; CSS 3D itself runs on the compositor.
- **Nothing is promoted permanently.** No element has a `will-change` other than `auto`, at rest or mid-sequence. GSAP promotes only while it animates.
- **Layout shift.** 0.018 on desktop and 0.006 at 390 px, the same as the static fallback; the remaining shift is the web-font swap on the cover. The first version of revision 2 measured 0.64 and 1.0 here, caused by the fail-safe itself; see [04 § Activation and fail-safes](04-motion-spec.md#activation-and-fail-safes).
- **Static fallbacks** were measured too: they request fewer images over the same scroll, and their style and layout cost is near zero.

**What it does not say:** how a real mid-range phone's GPU handles the composited layers, or LCP over a real network with compression. Those need a device test and a production build.

## Performance risks

| Risk                                                    | Likelihood                     | Impact                                                                                          | Mitigation                                                                                                                                                                                                                                                                                                                     |
| ------------------------------------------------------- | ------------------------------ | ----------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| Compositor load from five 3D layers plus the screenshot | Medium (desktop), Low (mobile) | Dropped frames during the tilt on low-end hardware; the scrub smoothing hides small hitches     | Done in revision 2: under 900 px there is no 3D stack (one flat sheet and a 2D section), the boundary and floor are not rendered, and nothing uses permanent `will-change`. | LCP on the cover                                        | Low                            | The LCP element is the name (text).
